# 额度推荐算法 · 分层 EDF（Earliest Deadline First）

## 核心逻辑

**目标：在所有"当前可用"的服务商里，找出最应该现在去用的那一个。**

分两步：先筛资格，再分层排序。不用单一阈值，用多档分层，避免临界点附近的误判。

---

## 第一步：资格过滤（Gate）

只保留同时满足以下两个条件的服务商，不满足的直接排除，不参与后续排序：

```
weekly_remaining_pct > 0      // 周额度还没用完
five_hour_remaining_pct > 0   // 5小时额度还没用完（否则现在实际调不了）
```

两个条件都是硬性门槛，不是打分项，不加权重。

---

## 第二步：分层排序（Tiered EDF）

按"距离周额度刷新的剩余小时数"划分层级：

```
Tier 1: reset_hours < 6
Tier 2: 6 ≤ reset_hours < 24
Tier 3: 24 ≤ reset_hours < 72
Tier 4: reset_hours ≥ 72
```

排序逻辑：

```
1. 从 Tier 1 开始检查
2. 若该层存在满足门槛的候选，取该层内 weekly_remaining_pct 最高的一个，返回，结束
3. 若该层为空，进入下一层，重复步骤 2
4. 若 Tier 1~3 均为空，从 Tier 4 中取 weekly_remaining_pct 最高的一个
5. 若所有层都没有满足门槛的候选，返回"无推荐"（不强行推荐一个用不了的服务商）
```

---

## 关键设计原则（为什么这样设计）

1. **层内按剩余量排序，而不是按刷新时间排序**
   同一层内，越快到期的不一定越该推荐——剩余量才是"能抢救多少"的真实指标。例：Tier 3 内 A 剩 20%、47小时后刷新，B 剩 95%、49小时后刷新，应推荐 B。

2. **不用单一硬阈值（比如"48小时内"）**
   单一阈值会在边界产生悬崖效应：47小时的候选被选中，49小时但剩余量大得多的候选被直接排除。分层结构把边界问题的影响范围限制在层内比较，而不是层间的非此即彼。

3. **5小时额度只做门槛，不参与排序打分**
   5小时额度刷新太快，拿来做紧迫度计算没有意义，只用来判断"现在能不能实际调用"。

4. **不引入连续函数（如 剩余% ÷ 距刷新小时数）**
   这类公式在分母趋近 0 时数值会失真，且排序结果不直观，用户看到推荐结果需要反向验证逻辑，不适合一个一眼扫过的 menubar 小工具。

---

## 可调参数

层级边界（6h / 24h / 72h）不是固定值，按你实际检查 App 的频率调整即可，比如你一天只看一次，可以把 Tier 1 改成 12h。层级数量和边界值可调，但"分层 + 层内按剩余量排序"这个结构本身不需要再改。

---

## "无推荐"状态：何时会触发，不能被忽略

**"无推荐"不是理论边界情况，是必须处理的真实状态。** 它和"各服务商重置时间是否相同"完全无关，只取决于第一步的资格过滤——只要在某一时刻，没有任何一个服务商能同时满足 `weekly_remaining_pct > 0` 且 `five_hour_remaining_pct > 0`，推荐就为空。

会触发"无推荐"的典型场景：

1. **所有订阅的周额度都已耗尽**（`weekly_remaining_pct = 0`）
   多个服务商重置时间不同，只能保证它们不会同时"重置"，不能保证它们不会同时"用完"。使用密集时，5 个订阅完全可能在同一时间窗口内全部归零。

2. **所有订阅周额度未耗尽，但 5 小时额度全部用完**（`five_hour_remaining_pct = 0`）
   这种情况比第 1 种更容易发生，比如短时间内密集调用多个工具，5 小时窗口被同时打满，即使周额度还有大量剩余，此刻也无法推荐任何一个。

**"无推荐"状态的处理原则：**
- 不强行推荐一个此刻实际不可用的服务商
- UI 应明确展示"无推荐"或类似提示，说明当前所有服务商都受限，而不是留空或报错
- 可选：提示最快恢复可用的服务商及恢复时间（即 `five_hour_remaining_pct = 0` 的服务商里，5小时额度最快重置的那一个），作为"无推荐"状态下的辅助信息

---

## 订阅数量对算法的影响

- **算法逻辑（Gate + 分层排序）不因订阅数量变化而改变**，1 个订阅和 5 个订阅走的是同一套判断规则。
- **1 个订阅时，推荐页依然有意义**：此时算法退化为"判断这一个订阅现在能不能用"，而不是"从多个里选一个"。例如唯一订阅的 5 小时额度耗尽时，推荐页应正确显示"无推荐"，而不是因为只有一个候选就跳过门槛判断直接展示它。
- **只有"查看额度"这个对比页在 1 个订阅时失去意义**，因为对比类展示本身需要多个对象才成立，退化为单条数据展示。这一点不影响推荐算法本身。
